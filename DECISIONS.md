# Decisions

Choices the brief (`docs/SPEC.md`) does not specify, one entry per choice, newest last. Status is *proposed* until the plan in `docs/PLAN.md` is approved, then *accepted*; a superseded entry keeps its number and points to its replacement. Section references (§n) are to the brief; Q-numbers refer to `docs/PLAN.md` §9.1.

| # | Decision | Why | Status |
|---|---|---|---|
| D-001 | Clave Studio replaces the EqualScore demo at the repository root; the demo stays reachable as tag `equalscore-demo-final` and branch `equalscore-demo`. | One repo, one deploy target; `netlify.toml` and the old README describe another product. | proposed (Q1) |
| D-002 | Toolchain: Node 22, pnpm 10, Next.js 16 / React 19, TypeScript strict, Tailwind 4, shadcn/ui, next-intl 4, Vitest, Playwright; versions pinned. | Current stable releases; upgrades are their own PRs. | proposed |
| D-003 | One `people` table for students and guests (`kind` column, nullable `user_id`), separate from `memberships`. Charges, payments, attendees and check-ins reference `people`. The brief's guest note is `people.note`, visible to the person. `people.phone` is the canonical WhatsApp number per school; `profiles.phone` is only the user's default. | §5 "person = student or guest", §5 guest conversion "keeping their history", §10 admin-created students before login. | proposed |
| D-004 | Business status (`pending`/`active`/`inactive`) lives on `people`; `memberships.status` mirrors it by trigger for students. The `[slug]` gate is three-way: active → app, pending → waiting card, otherwise 404. | A student who never logs in has no membership to be active; a pending student must see that they are pending. | proposed |
| D-005 | Every business table carries `school_id` and children use composite foreign keys `(x_id, school_id)`. | Cross-tenant references become impossible at the database level. | proposed |
| D-006 | RLS helpers are argument-less `security definer` functions in a non-exposed `private` schema; every RPC starts with `assert_admin`/`assert_member` on a school derived from the entity id; no `force row level security` on `memberships`/`people`. | No policy recursion, one InitPlan per statement; RPCs cannot forget the tenant check (lint). | proposed |
| D-007 | Logic split: numbers and explanations shown to humans are pure TypeScript (`src/lib/domain`); anything atomic with a write or deciding what the database does (generation, sync, window match, overlaps) is SQL. Nothing exists twice; TS display helpers are labelled as such. The monthly run computes in TS and inserts through one SQL function. | §6 "one pure, well tested function" and §19 testability. | proposed |
| D-008 | Activity log is one trigger (`00_log_activity`) on every business table; RPCs set `app.event` and `app.reason`; jobs set actor settings; derived inserts of pristine rows during generation/sync are not logged (`app.system_op`, restored on exit); a write with no actor raises. Reasons for edits, voids and removals live only in the log. | §11 "nothing slips through"; readable log; misuse of the service key fails loudly; students never read admin remarks. | proposed |
| D-009 | Locale comes from user preference and a cookie, never from the URL; next-intl runs without routing. The sign-in email is bilingual. | Printed URLs must not change; §16 "switch per user"; Supabase has one email template per project. | proposed |
| D-010 | Every app URL is scoped by school slug (`/{slug}/...`); the layout resolves membership once per request. | §4 several schools per user, shareable links, no server-side "current school". | proposed |
| D-011 | Public self-registration requires sign-in first, then a two-field form, and always produces a `pending` person; an email match with an existing student is a hint on the approval screen, never an automatic link. | Verified email, no bot pile, immediate "pending" screen; an admin-typed contact email is not proof of identity. | proposed (Q7) |
| D-012 | Admin-created students are `active` immediately; self-registered students are `pending` until approved. | §10; the teacher already vetted the people he types in. | proposed |
| D-013 | Admins may invite and deactivate other admins; only the owner row is protected (trigger); ownership transfer is v2. Every user has "sign out everywhere". | §4 "same rights as owner", "cannot remove the owner"; lost-phone recovery. | proposed |
| D-014 | QR tokens live in `location_qr_tokens` (one active per location, rotation-ready) rather than a column on `locations`. The printable QR is a print-ready page, not a PDF. | Students never read tokens; §9 "keep the design open for a rotating QR". | proposed |
| D-015 | A single dated class is `kind = 'regular'` with `slot_id null`; regular needs a category, not a slot. | §9b: auto expected list and counting by default. | proposed |
| D-016 | Slots and sessions store wall-clock times; `starts_at`/`ends_at` are derived by trigger through the school timezone; `weekday` is ISO 1–7 and immutable; SQL uses `private.local_date(school)` for every "today" (lint-enforced). | DST correctness; idempotent generation on `(slot_id, slot_date)`; Supabase's `current_date` is UTC. | proposed |
| D-017 | Expected attendees are materialised rows kept right by one idempotent `recompute_expected`; removals are tombstones; walk-ins are a source value; pristine sessions are defined precisely and attendee rows cascade on their deletion. | Plain selects for agenda counts, portal and RLS; §9b "clearly marked". | proposed |
| D-018 | QR check-in to an extra session is only possible for people on its expected list; regular sessions accept any active student (flagged if not enrolled); pending students cannot check in. | §9 literal; prevents accidental `attended` charges. | proposed (Q8) |
| D-019 | A check-in never sets `attended`; the review's one tap or confirming the review does; confirming turns remaining `expected` into `absent`; `confirm_session_charges` marks reviewed first and previews against post-review statuses. | §5 "status is the teacher's confirmed truth after review"; what is shown is what is written. | proposed |
| D-020 | Counting toward the allowance is kind-aware: extras count iff their toggle is on; regular sessions count iff the toggle is on and the category is limited. No overuse flag when the student has no limited category; unenrolled attendances in limited categories count; manual adds are not flagged as unenrolled. | Resolves §5/§9 conflict for unlimited categories and §9's extra-rehearsal example. | proposed (Q9) |
| D-021 | Best cover: maximise covered categories, then lowest total, then fewest rules, then rule ids; rules are exact category sets; a rule pricier than its parts still wins by coverage with a warning at save time. | §6 literal order, deterministic explanations. | proposed (Q5, Q6) |
| D-022 | Every charge (monthly and one-off) has a `period` (first of month); status is a stored generated column with a `void` value; charges are voided, never deleted; all charge writes go through RPCs; edits require a reason and optimistic concurrency. | §9b one-offs land on a month; §7 editable and logged. | proposed |
| D-023 | Monthly run: hourly tick, per-school local date, ledger claim/finish RPCs (service role only), "no completed run for this period" as the condition, eligibility by activation date on or before the 1st, `billing_start_period` set at school creation and editable in Settings; "Generate now" is a server action running the same job with admin attribution. | §3 timezone per school; self-healing after outages; no surprise first bill; no client-supplied charge rows. | proposed |
| D-024 | Proration: calendar days including the join day (local date of activation), half-up integer arithmetic, a suggestion the admin confirms; "no charge" creates a $0 charge with the reason. | §7 leaves the basis open. | proposed |
| D-025 | One payment ↔ one charge; `record_payments` writes several rows in one transaction with a `client_key` per row (identical replay is a no-op, a different payload is an error); overpayment and payments on void charges refused; no credit balances in v1. | §5 literal; smallest correct ledger. | proposed (Q4) |
| D-026 | Every one-off charge belongs to a `charge_batches` row with a `client_key`, so creation is idempotent even for one person. | A retried submit must not double-charge a team. | proposed |
| D-027 | Income split uses a `breakdown` JSON snapshot per charge (rule price allocated to categories proportionally to default prices, largest-remainder rounding) scaled at read time. | §12.4 with rules spanning categories; no extra tables or triggers. | proposed |
| D-028 | Scheduler: Vercel Cron hourly on the Pro plan calling `/api/cron/tick`; `pg_cron` + `pg_net` is the drop-in fallback; the route is scheduler-agnostic and writes a `tick` ledger row per hour. | Hobby crons are daily and non-commercial; the "last run" badge needs data from M1. | proposed (Q2) |
| D-029 | Live check-in lists poll every 10 s while open; Supabase Realtime deferred. | One data path; the list is watched for a minute after class. | proposed |
| D-030 | Database tests are Vitest + `pg` (not pgTAP) so they run against the Supabase CLI stack and against a plain Postgres 16 with an `auth` shim; suites needing PostgREST/GoTrue run in CI only. | One runner; the cloud build environment has no Docker. | proposed (Q11) |
| D-031 | Full core schema, RLS, activity trigger, cron transport, Settings and a bare activity list ship in M1; a read-only student list with the pricing card and override editor in M2; Team, the WhatsApp helper and "sign out everywhere" in M3; extras-only-if-expected, guests and the admin attendance tab in M5; extra-session charging is a separate re-runnable step in M6. | Each milestone must be hand-testable; §18.1's seed needs the whole schema. | proposed |
| D-032 | Migrations are append-only across milestones; one squash at go-live; staging is reset at each milestone; production is never seeded; the seed runs as `postgres` with `app.actor_label = 'seed'` and calls the generation/charge RPCs once they exist. | Clean history, safe testing, seed states the app could produce. | proposed (Q10) |
| D-033 | Code, commits, README and DECISIONS in English; UI default Spanish with English available. | Brief written in English; Chilean users. | proposed |
| D-034 | `schools.suspended_at` exists from M1 (no UI) and is honoured by the RLS helpers and the tick; legal pages ship in M9; account deletion is a manual runbook in v1. | Selling the product needs a freeze switch and a privacy page; deletion flow deferred. | proposed (Q12) |
| D-035 | Deferred from v1 as additive changes: in-database rate limiting, nonce CSP, Turnstile, Realtime, backfill of past sessions, admin-only private notes, PDF export, allocation ledger, per-location timezones. | Not asked for by the brief; each adds surface a one-school v1 will not miss. | proposed |
